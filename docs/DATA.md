# Data and provenance

ParcelResolve uses original synthetic records. No merchant export, customer message, payment record, carrier event feed, or external benchmark dataset was downloaded or used to claim results.

| Artifact | Purpose | Provenance and rights |
|---|---|---|
| `parcelresolve/seed.py` | Interactive development demo, orders 1042–1048 | Authored for this project; fictional customers and orders |
| `tests/fixtures/pre_label.json` | First development acceptance fixture | Authored for this project; synthetic GBP cancellation |
| `evaluation/catalog.json` | 40 distinct evaluation scenarios, orders 71001–71040 | Independently authored synthetic requests, identities, prices, addresses and initial states; original records offered under CC0-1.0 |
| `evaluation/manifest.json` | Provenance, creation timestamp, split rules and limitations | Project-authored metadata |
| `evaluation/intake-development.json` | Three distinct development-only model probes | Original synthetic text; no training or fine-tuning |
| `tests/fixtures/intake-recorded.json` | Exact recorded outputs for development contract tests | Original CC0-1.0 synthetic fixture, explicitly `recorded-fixture`; not generated by AI and never scored as AI |
| `evaluation/intake-benchmark.json` | 36 new requests: 12 cancel, 12 address, 12 unknown | Original synthetic text and annotations, CC0-1.0; authored and frozen before the first full comparison |
| `evaluation/model-comparison-freeze.json` | Pre-run prompt/config/grammar/corpus hashes | Frozen at 2026-10-14 03:41:12 UTC; no selection or tuning on comparison results |
| `model_assets/local-model.json` and `licenses/` | Pinned genuine local inference artifacts | Official Qwen GGUF weights, Apache-2.0; official llama.cpp runtime, MIT; exact revisions/hashes and source links retained |
| Evaluation `traces.jsonl`, `seeds.json`, `results.json` | Measured local executions and replay inputs | Generated by the evaluator from the catalog and simulator; actual UTC timestamps |

The catalog contains invented recipient names, two line items per order, GBP/USD/EUR minor-unit totals, linked order/shipment/label identifiers, target addresses and explicit expected outcomes. Addresses such as “Fictional Orchard Road” and the example postcodes are test inputs, not verified deliverable destinations. JPY and fractional quantities appear only in cases that require validation to reject them.

`fixture_order()` in `parcelresolve/evaluation.py` maps evaluation records into the same typed `OrderSnapshot` accepted by the application. It never imports `seed_demo()` or `make_order()`. Transformation consists of integer quantity/price multiplication, deterministic resource-ID construction, typed model validation, and creation of time-bounded synthetic warehouse evidence. No floating-point amount calculations, identity fuzzy matching, or inferred refund allocation occur.

Development and evaluation are separate files and disjoint order namespaces. The catalog does not reuse the demo's names, addresses, captured amounts or line IDs. Both the baseline and intake profile receive identical provider inputs and seeded event schedules. The deterministic interpreter receives customer text only; neither terminal-state gold nor the catalog's operator-selected intent is supplied to it. The SOP baseline explicitly receives the intent selected by an operator. All consequential actions remain governed by the same backend evidence and approval checks.

This is an openly available engineering acceptance corpus. Its scenarios are visible to the implementers, and failures were used to fix implementation and grader defects. The split prevents accidental use of demo seed records as evaluation records; it does **not** make this a sequestered benchmark, justify statistical generalization, or establish model accuracy. Crash checkpoints and repeated schedules are multiple trials of a scenario, not additional independent examples.

The default seeds are 7, 19 and 41. Each scenario/seed pair derives its own `random.Random` seed from SHA-256, chooses the initial observation delivery stage, and permutes current, delayed and duplicate final observations. The runner writes the exact schedule, input catalog, catalog hash, source hashes, raw event deliveries, operation boundaries and separate provider/ledger databases. UUIDs and wall-clock timestamps vary between reruns; expected outcomes and delivery schedules are reproducible. Concurrent operating-system thread scheduling is intentionally not claimed to be controlled by the event seed.

No customer messages are sent. Local drafts, requests and provider snapshots are retained in evaluation traces because every record is synthetic. A future merchant-data profile needs explicit access permission, a retention policy, privacy review, identifiers separated from model inputs, and a genuinely independent case split before its results can be reported as real-world evidence. Public API documentation was consulted for adapter contracts; documentation text is not an evaluation dataset.

## Frozen intake comparison

The intake corpus is separate from the 40 recovery acceptance scenarios, the three development probes, the two recorded contract fixtures, and existing intake test messages. No exact input text is reused. Each annotation follows the written guideline: an unambiguous whole-order cancellation, a delivery-destination correction, or clarification for ambiguity, conditions, negation, conflicting actions and unsupported scope. Annotations were authored before model predictions. No external dataset, merchant record or generated model answer was used as a target. The benchmark runner checks corpus/config/prompt hashes and development-text disjointness before inference.

The first full comparison began at 2026-10-14 03:49:39 UTC, after the 03:41:12 freeze. All 36 requests were run through the shipped deterministic interpreter and actual pinned Qwen CPU inference at seeds 7, 19 and 41. Expected labels remain in the grader only; the interpreter receives customer text only. The existing prompt-injection/unsupported-scope guard is shared; its six guarded local-profile trials are labeled deterministic and counted as zero model calls. Seed repetition produces 108 trials per profile, not 108 independent examples. Temperature zero produced identical predictions across seeds.

Only the first of the three development probe texts was executed before the freeze to establish the local runtime and accounting contract. No model training, fine-tuning, prompt search, second model selection or post-result tuning was performed. The recorded fixture provider and mocked transport/runtime unit tests verify contracts only; they are excluded from measured model results. The benchmark's worse local-model score and individual errors are retained rather than filtered.

Corpus SHA-256: `3a7e1678430631c43d03ae629dd609b72746da9ede34868cce65bd71f431d712`. Frozen system prompt SHA-256: `09b7e0839b209a2f69b29576b1a3b026ca05f069ae26d88a7dc80bc14966ebaa`. The [freeze](../evaluation/model-comparison-freeze.json) includes all other hashes. The [retained run](../evaluation/results/local-ai-2026-10-14/results.json) records code hashes, machine architecture, runtime counters and timestamps; raw JSONL includes exact outputs and runtime logs.

“Held out” here means withheld from runtime development/probing and frozen before comparison, not hidden from the implementer who authored its labels. This one-pass synthetic comparison cannot estimate real merchant accuracy, safety or handling time. The openly visible recovery acceptance catalog may be used to fix engineering defects; the separate intake corpus was not used to tune interpretation after results became available.

The same unchanged model subsequently ran the 40 visible recovery scenarios at three event seeds. This second experiment tested the workflow integration, not a new held-out classification corpus. Its 45 failing trials, including 42 wrong-intent false resolutions under synthetic auto-approval, are retained at `evaluation/results/local-ai-workflow-2026-10-14`; no failed records were replaced or relabeled. The observed failures led to rejecting local-model mode from the operator API. Current passing deterministic/SOP evidence is separately retained at `evaluation/results/verified-2026-10-14`, with warehouse intent and receipt audit records. Both workflow runs retain losslessly compressed traces and simulator/ledger databases with checksums and documented restoration commands.
