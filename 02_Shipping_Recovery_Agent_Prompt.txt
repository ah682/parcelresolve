BUILD PROMPT 2 - WOOCOMMERCE / SHIPSTATION EXCEPTION RECOVERY

PROJECT OBJECTIVE
Build "ParcelResolve", an operator-facing recovery desk for WooCommerce merchants using ShipStation. It handles order cancellation or address-change requests when storefront, payment, label, shipment and warehouse states disagree. The useful outcome is a verified recovery or a correct escalation, with evidence and an audit trail.

The distinction is current-version exception handling and verification. Ordinary refunds, address changes and multi-app actions already exist. Do not assume historical plugin bugs still exist: the WooCommerce ShipStation plugin added refund/return support in April 2026 and continues improving. Confirm actual integration capabilities before writing adapter assumptions.

FIRST RELEASE SCOPE
One store, one warehouse and three flows: cancellation before label creation; cancellation after label creation but before confirmed dispatch; and address correction requiring label recreation. Include partial shipments in monitoring and evaluation, but require operator review for complex split-shipment recovery. Exclude subscriptions, chargebacks, cross-border tax changes, carrier interception and arbitrary 3PL integrations.

Default to a fully functional local simulator. Suggested stack: typed Python API, PostgreSQL for case/action ledger and concurrency, a focused TypeScript UI or a simpler maintained UI, and a durable workflow runner. A standard state machine is acceptable; adopt LangGraph or another engine only if it simplifies persisted recovery. Supply one command to start/reset the demo.

DOMAIN AND INVARIANTS
Keep these distinct: order commercial state; payment/refund state; line quantities; label status; shipment status; physical warehouse dispatch; and customer notification status. ShipStation's "Shipped" can mean a label was printed. Never infer physical dispatch from that status alone.

Create typed models for order snapshot, line item, refund, shipment, label, warehouse acknowledgment, customer request, recovery case, proposed action, approval, operation attempt and evidence event. Represent money with currency-aware fixed precision/minor units; never floating-point arithmetic. Explicitly reject unsupported quantity/currency cases rather than rounding or guessing.

Implement a persisted lifecycle such as received, investigating, needs-information, proposal-ready, awaiting-approval, executing, reconciling, resolved, escalated and failed. Define permitted transitions and invariants. A case can only be resolved when read-back checks establish its intended terminal state or the operator records a supported resolution.

RELIABLE ACTION EXECUTION
1. Normalize identities across WooCommerce order IDs, ShipStation order keys/IDs, shipment/label IDs, refunds and line quantities. Verify mappings against the actual API product/version used.
2. Create a read-only joined timeline and detect refunded/cancelled items assigned to active shipments, stale tracking, duplicate active labels and mismatched quantities.
3. Derive permitted actions from backend rules, authenticated operator permissions and observed state. Let the model interpret text and ask clarifying questions; do not let free-form model output define refund amounts, authorization or warehouse truth.
4. Require explicit approval for proposed refunds, label voids and replacements in the first release. Bind approvals to the case, action hash, resource version and amount. Revalidate after approval if state changed; stale approval must not authorize a different action.
5. Persist operation intent before an external write. Use provider idempotency where supported and record provider identifiers. On a timeout after a possible write, query/reconcile before retrying. If the outcome cannot be established, escalate. Never claim exactly-once external side effects unless the provider supports the necessary guarantee.
6. Use per-resource locking/concurrency control, precondition checks, read-back verification and durable restart recovery. External effects must not be blindly replayed after workflow restart.
7. Distinguish compensation from true rollback. A refund, carrier handoff or label action may be irreversible or subject to provider limits. Report partial completion and the remaining operator action.
8. Require a positively acknowledged, current warehouse hold/stop before treating a post-label parcel as safely cancellable. Missing dispatch confirmation, an old snapshot or a label status is insufficient. Revalidate the hold and physical state at the action boundary; if dispatch races with the approved recovery, prevent an unsafe completion claim and escalate. Where the warehouse cannot provide a reliable hold acknowledgment, keep the case operator-controlled.
9. Draft customer explanations locally but do not send messages. Avoid saying a package is stopped until the warehouse/dispatch evidence supports it.

ADAPTERS AND MODES
Provide interfaces and working local adapters for commerce, payments, shipping and warehouse confirmation. Implement realistic fault injection: before-write failure, successful write with lost response, delayed events, duplicate delivery, stale reads, rate limits and unavailable service. Provide configurable real WooCommerce and ShipStation adapters only for documented supported contracts; unsupported endpoints must raise an explicit capability error, never return success-shaped mock data in live mode.

Real adapters default to read-only. Live mutations require an explicit configuration gate plus owner authorization and the product approval workflow. Keep secrets server-side. ShipStation sandbox lacks webhooks and simulated tracking: local fault simulation is essential, and sandbox results do not establish carrier/warehouse recovery.

MODEL BEHAVIOR
Use structured request interpretation with validation, ambiguity handling and identity supplied by trusted context. Injected instructions in customer notes must not alter policy or disclose other orders. Provide a deterministic demo interpreter and a real model adapter. Compare AI-assisted intake with a deterministic case desk; keep the AI component only where it helps interpretation or handling time.

MANDATORY ACCEPTANCE SCENARIOS
- Pre-label cancellation reaches a consistent supported final state.
- A printed label with unknown dispatch triggers warehouse confirmation.
- The external refund succeeds but its response is lost; restart/reconciliation does not refund twice.
- Cancellation succeeds and refund fails; the case remains visibly incomplete.
- Old label void succeeds and replacement creation fails; the case is recoverable and not falsely resolved.
- The carrier rejects a void; the operator receives a correct escalation.
- Two operators act on the same case; conflicting writes are prevented/reconciled.
- A customer changes the order outside the desk after approval; preconditions invalidate the plan.
- A parcel dispatches between approval and execution; the stale plan cannot produce a false stopped/cancelled result.
- Duplicate and out-of-order events do not regress established state.
- A partially dispatched order cannot be handled as wholly cancellable.
- Unauthorized order access and prompt injection cannot trigger mutations.
- Process termination at every mutating boundary preserves recovery information.

EVALUATION
Grade intended terminal state and necessary communication, not an identical sequence of tool calls. Start with at least 30 distinct scenarios and several seeded event schedules. Report correct resolution/escalation, false resolution claims, duplicate effects, stale tracking, invariant violations, restart recovery, operator steps and model cost. Compare with a deterministic integration/SOP baseline. Persist raw traces and event seeds.

PRODUCT EXPERIENCE
Provide a case queue, joined evidence timeline, disagreement indicators, proposed actions, approval controls, execution status and audit history. Show the distinction between printed, awaiting warehouse confirmation and physically dispatched. Make partial failure understandable to an operator without exposing internal framework details.

RELEASE GATES
The offline demonstration must complete the three supported flows, reproduce lost-response recovery and pass invariant tests. Document real API contract checks actually run. List unverified live-carrier/merchant capabilities separately. Merchant adoption and handling-time gains require later authentic cases; do not invent them.
